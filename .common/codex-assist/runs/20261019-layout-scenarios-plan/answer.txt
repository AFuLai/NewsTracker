## 2. 事件地圖（四個方案）

### 2.1 我們已有的資料

**F2** `tracker/render.py:127` `"sources": _parse_sources(r),`

- 驗證：`sed -n 116,127p /opt/tracker/repo/tracker/render.py | grep -oE '^ +"[a-z_]+":'`
- 輸出為十個欄位：`id, trackers, category, title, summary, tags, title_en, summary_en, tags_en, sources`。
- **沒有** cluster、event、date、地理或實體欄位。日期來自檔案 key（L1973 的 `_date`）。
- UI 對文章的 `a.cluster / a.date / a.entities / a.geo / a.severity` 引用為 **0 處**。
- `cluster` 目前只屬於 CRA 圖書庫的主題，不屬於新聞（L1554、L1626 `function libGroupKey(t, sources) {`）。
- 「事件群集」的實作是 `tracker/cluster.py:86` `def merge_by_title(rows`。它只在**同一天**內合併，只留下 `sources`，不持久化 event id。呼叫處在 `tracker/orchestrator.py:1172` `from .cluster import merge_by_title`。
- 資料庫的 `articles` 表已有 `embedding BLOB`，`written` 的 12801 筆中 6754 筆有向量。這些向量**沒有輸出到前端**。
- 量化結果：
  - 多來源文章 109 / 12639（0.9%，最多 5 個來源）。
  - 帶 `CVE-*` 標籤的文章 2511 / 12801（`written`，查詢條件 `tags like '%CVE-%'`）。
  - 平均每篇 6.01 個標籤（來自前述 `data-*.js`）。

### 2.2 方案

| 方案 | 已有 | 缺少 | 函式庫成本（CDN、無 build） |
|---|---|---|---|
| **A. 依事件的時間軸**（推薦首選） | `tags` 內的 CVE、`sources`、日期 | 跨日 `event_id`。可先用 CVE 當事件 key，涵蓋約 20%。其餘要靠標題相似度或 embedding 在 pipeline 端跨日聚類。 | 0：純 DOM/CSS，沿用 `.date-divider`（L602）與 `lib-row`（L689 `buildLibRow`）樣式。 |

## 3. 新聞內容框架化

### 3.1 欄位對應

| 框架欄位 | 現有來源 | 需 LLM／pipeline |
|---|---|---|
| What（標題、摘要） | `title/summary`（L2055–2056） | 否 |
| When（發布日） | 日檔 key（L1973） | 事件**發生日**與發布日未區分，需 LLM（例如摘要裡的「10月2日至10月7日」） |
| 分類 | `category`，經 `effectiveCat`（L1366） | 否 |
| 影響平台 | OS tracker 的 `category`（Linux/Windows/Apple/Android，L1360–1363） | 否（僅限 OS tracker） |
| 識別碼 | `tags` 的 CVE 正規式（L2048） | 否 |
| 證據與可信度 | `sources[{name,url,lang}]`、`sources.length` | 否 |
| Who / Where / Why / How | 無 | 需要 |
| Affected products（含版本） | `tags` 部分有，但沒型別 | 需要 |
| Impact / severity | 無 | 需要（或查外部 CVSS，語意見 3.3 的 gap） |
| Timeline、event_id | 無 | 需要（跨日聚類，見 2.2） |

### 3.2 建議的資料形狀

在日檔項目加一個**選填**的 `frame` 物件：

```
frame: { event_id, who, where, why, how, impact, products[], severity, event_date }
```

- 沿用 `data_day.js.j2` 的做法：有值才輸出（該模板對 `title_en` 就是 `{%- if item.title_en %}`），UI 缺欄位時整區不顯示。
- 前端在 `openOverlay`（L2080）渲染框架區塊，`buildCard`（L2036）只露出 `severity` 與 `event_id`。
- pipeline 側會多一次 LLM 呼叫，或擴充現有摘要 prompt。我**沒讀** `tracker/prompts/`，擴充方式屬假設。

### 3.3 需要裁決的缺口

```
CODEX-ASSIST-GAP

  question: severity／impact 的等級定義（幾級、判準，是否引用 CVSS／KEV）
```

### 4.1 佈局與預設

### 4.2 儲存：單一 key `tracker_view`

```
{ "v": 1, "preset": "quick", "overrides": { "layout": "river", "density": "compact" } }
```

- **只存 preset id 加使用者覆寫值。** 預設的定義放在程式碼的 `PRESETS` 常數，改定義時不需要遷移資料。`v` 只管儲存格式。
- **版本與壞資料：** `JSON.parse` 失敗、`v` 不認得、`preset` 不在 `PRESETS` 中，一律回到「預設」。不覆寫壞值，直到使用者下次改動。
- **storage 丟例外：** 沿用現有慣例，每次存取包 `try { … } catch (e) {}`（L1019 起、L1098 等）。失敗時改用記憶體內的 `viewPrefs`，本次工作階段有效，不報錯。
- **優先序**（與現有一致，L1473 `if (!applyHashRestore()) selectTracker(names[0]);` 與 L2308 的 skin 先例）：URL hash `p=` 勝過 localStorage，localStorage 勝過預設。
- **與現有五個 key 的關係**（`tracker_lang/theme/skin/nav/lib_group`，各 2–3 次引用，已用 `grep -oE` 計數）：
  - 這五個 key 都不動。
  - theme 與 skin 是獨立軸（L11–13 的註解），不納入 preset。
  - preset 的導覽預設值只在 `tracker_nav` 未設定時才生效，使用者明確設定過的 `tracker_nav` 優先。
- **預覽模式：** `pv=1`（見第 5 節）時不寫入 localStorage。

## 5. Console 本機預覽

### 5.1 現況

- `tracker/web_dashboard.py:228` `def do_GET(self):` 對 `/state` 以外的所有路徑一律回傳內嵌的 `_HTML`（L236–241，L237 `body = _HTML.encode("utf-8")`）。
- 「預覽發布」按鈕（L498）呼叫 `deployCmd({cmd:'deploy', channel:'preview'})`（L792）。
- 這會走 `tracker/deploy.py:80` `args = ["hosting:channel:deploy", channel]`，是遠端 Firebase 預覽頻道，timeout 900 秒（L86），而且只能在 `afu-delta` 執行。
- 網站輸出目錄是 `tracker/__init__.py:25` `DEFAULT_OUT = ROOT.parent / "web" / "public"`。
- `ui/index.html` 只在 render 時才複製過去（`render.py:222` `shutil.copyfile(src, dst)`）。

### 5.2 最小設計

1. **伺服器：** 在 `do_GET` 的 `else` 前新增 `/site/…` 分支。
   - 對應到 `DEFAULT_OUT / 相對路徑`。
   - 去掉 query 與 hash 後做 `resolve()`，並檢查 `is_relative_to(DEFAULT_OUT.resolve())`，防路徑穿越。
   - 以 `mimetypes` 決定 Content-Type，加 `Cache-Control: no-store`，找不到就回 404。
   - 只做 GET、只讀，不碰 `/control`。
   - `/site/index.html` 直接讀 `ROOT/ui/index.html`，這樣改 UI 不必先 render 就能預覽。
   - 綁定位址維持預設 loopback（L264）。
2. **頁面：** 在 Publish 卡（L489–502）之後新增 `<section class="card" id="sec-preview">`。內容為：
   - preset 下拉（含「預設」）。
   - 寬度下拉（桌面／平板 820／手機 390，只改 iframe 寬度）。
   - 「本機預覽」按鈕：把 iframe 的 `src` 設成 `/site/index.html?pv=1#p=<preset>`。
   - 「新分頁開啟」連結。
3. **獨立於輪詢：** `poll()` 每 800 毫秒跑一次（L826），`syncDeploy`（L804）只改文字，所以放在獨立 section 的 iframe 不會被重置。
4. **命名：** 現有「預覽發布」（L498）容易與本機預覽混淆，建議改成「預覽頻道發布」。措辭由你決定。
5. **測試：**
   - 仿 `tests/test_web_dashboard.py:48`（`test_http_server_serves_state_and_html`）測 `/site/index.html` 回 200，並用 monkeypatch 換掉 `DEFAULT_OUT`。
   - 測 `/site/..%2f..%2fetc/passwd` 回 404 或 403。
   - 仿 `tests/test_dashboard_publish.py:87`（`test_html_has_publish_card`）加字串檢查 `id="sec-preview"`。
